# `src/features/` - Tiered Feature Engineering and Working-Set Construction

**Status:** Google and Backblaze modules populated (Phase 3) plus the RQ2 conflict labeler (Phase 4). The Google Tier 1/2/3 builders (`historical`, `scheduling`, `temporal`, `runtime`, `utilization`), the scheduled-episode regrain (`episodes`), the working-set sampler (`sampling`, now with both the Google and Backblaze paths), the Backblaze SMART feature module (`backblaze_smart`), and the RQ2 conflict labeler (`conflict_labels`) are extracted and validated. Modules are extracted after the notebooks validate the logic against the EDA-informed feature priority documented in `eda_decisions.csv` (`V13` for Google tier structure, `V14`/`V15`/`V19` for Backblaze SMART features).

## Modules (Google)

- `historical.py` - Tier 1 historical signals derived from the lifecycle summary: `prior_fail_count`, `has_prior_fail`, `resubmission_count`, `prior_evict_count`, `first_resubmission`, `lifecycle_position`. Motivated by `V09` (rapid-onset failure model) and `V10` (resubmission history dominates).
- `scheduling.py` - Tier 1 scheduling and priority features: `priority_tier` (one-hot using the bands in `src/data/schemas.py`), `scheduling_class`, `platform_id`, `cpu_request`, `memory_request`, `request_ratio`. Motivated by `V07`. `priority_tier` and `scheduling_class` are sourced from the submit-time values (`submit_priority` / `submit_scheduling_class`, the first-event values in `instance_lifecycle_summary`), not the terminal (death-time) values, which would leak the outcome at the prediction point (`V35`). The platform one-hot is attached via the scheduled machine, an attribute observable at scheduling time rather than an outcome leak.
- `temporal.py` - Tier 1 submit-time temporal features: `submit_hour_of_day`, `submit_day_of_week`, sin/cos cyclic encodings, `submit_is_business_hours_pdt`, `submit_is_weekend`. Derived from `submit_time` in the lifecycle summary using the PDT wall-clock convention. Motivated by `V26` (FAIL_LOST rate varies up to ~8x across hour buckets).
- `runtime.py` - Tier 2 early-runtime features: `cpu_slope_{5s,15s,30s}`, `memory_slope_*`, `initial_cpu_ramp`, `initial_memory_ramp`, `first_interval_util_ratio`, `cpi_value`, `mapi_value` (conditional on `has_hardware_counters_majority`). Motivated by `V12` (utilization inversion: rate of change carries the signal).
- `utilization.py` - Tier 3 windowed utilization features: `avg_cpu_5min` / `15min` / `60min`, `max_cpu_*`, `std_cpu_*`, and the memory variants. Included for ablation per `V13`; expected predictive value is low because the rapid-onset failure window (median 23s) is shorter than the aggregation windows.
- `sampling.py` - Working-set construction for both datasets. **Google** (`P01`): `build_working_set_google(events_lf, target_size_M=75)` is the pure-Polars reference (retains every collection with a FAIL or LOST instance, stratified-samples successful collections by the joint `(priority_tier, scheduling_class)` distribution using submit-time strata keys so they never encode the outcome, `V35`, returning the LazyFrame and a `SamplingManifest`); `build_working_set_sql(...)` is the BigQuery production path. The eligible instance population (35.1M) is below the projected band, so the sampler returns the full eligible population with exact marginals; the band is met at the episode grain (notebook 10 Section 11.3). **Backblaze** (`V17`, `P07`): `build_working_set_backblaze(features, ratio=20, positive_column="failure_within_30d", strata_columns=("model_canonical", "year"))` operates on a materialized per-partition feature frame, retains every horizon-positive row (the union of the pre-failure windows), and undersamples the healthy class to `ratio:1` via a deterministic hash of `(serial_number, date)` applied uniformly, so the drive-model-by-year composition of the healthy sample matches the population (proportional stratified), returning the working set and a `BackblazeSamplingManifest`. The primary set is 20:1 with 10:1 and 40:1 sensitivity branches (`V46`). Tested in `tests/test_sampling.py` (Google: full failure retention, marginals within 2%, target-exceeds-population path, SQL render; Backblaze: all-positives retention, achieved ratio, strata-proportion preservation, no-op below target, determinism).
- `conflict_labels.py` - RQ2 conflict labeling (`P09`). Three pure-Polars labelers returning a shared envelope (`conflict_id`, `group_key`, `conflict_type`, `machine_id`, `start_time`, `end_time`, detection-time features, `resolution_outcome`): `label_resource_contention` (machine-window over-subscription of summed requests vs capacity), `label_priority_inversion` (an EVICT whose evicted instance outranks the replacing SCHEDULE within a short window, matched by an as-of join), and `label_scheduling_violations` (collection windows with abnormal SCHEDULE-to-EVICT / SCHEDULE-to-FAIL ratios, aggregated from the instance stream). `build_conflict_dataset(...)` unions the three. The shared `prior_counts(...)` helper counts each entity's FAIL/LOST and SCHEDULE events strictly before a detection timestamp (a union-plus-cumulative-sum giving strict less-than semantics), the leakage-safe way to attach the RQ1-dominant resubmission signal. Every feature is knowable at the conflict's `start_time`; `resolution_outcome` is failure-based (escalate iff an affected instance fails) and is never used as a feature; `group_key` (machine / instance / collection) is the entity the train/test split groups on. Validated in `notebooks/13_rq2_conflict.py`. Carries `V01`/`V08`/`V27` (label) and `V38`-`V40` (RQ2 design, history, split, result).
- `episodes.py` - Scheduled-episode (per-attempt) regrain that removes the instance-grain lifecycle-history leakage (`V30`). SQL builders: `build_episode_history_sql` (segmentation + strictly-prior history via the `sched_seq` construction and an `UNBOUNDED PRECEDING AND 1 PRECEDING` window), `build_episode_intervals_sql`, `build_episode_usage_subset_sql` (interval-assigned Tier 2/3 usage), `build_episode_runtime_features_sql` (reuses `runtime.slope_sql`), `build_episode_tier3_features_sql` (reuses `utilization._windowed_agg_sql`). Pure-Polars: `segment_episodes_polars` (testable mirror), `cap_negative_episodes` and `group_train_test_split` (modeling-stage helpers, `V32`). Motivated by `V30`-`V33`; carries `V01`/`V08`/`V27` (label) and `V09`/`V12`/`V13` (mechanism, tiers). Validated in `notebooks/11b`, `10` Sections 11-12, and `11` Section 3.8. At-submission `priority_tier` / `scheduling_class` in the episode base (notebook 10 Section 11.2) are sourced from the lifecycle summary's `submit_priority` / `submit_scheduling_class`, not the terminal values, which leak the outcome (`V35`; diagnosed in notebook 12 Sections 3.2-3.4).

## Modules (Backblaze)

- `backblaze_smart.py` - Per-drive SMART feature builders. Four pure functions, each computing its features within `over("serial_number")` on input sorted by `(serial_number, date)`, so no future row enters a past window (the leakage contract for the 2023-2025 temporal split). `add_tier1_smart_features` adds rolling non-zero indicators and days-since-first-non-zero on the primary SMART ids (5, 197, 198), one-hot manufacturer, and capacity (`V14`, `V18`, `V19`). `add_tier2_rolling_features` adds rolling mean / p95 / p99 / std and 1-day and 7-day rate-of-change on the primary ids plus a reduced set on the secondary ids (`V15`). `add_tier3_drift_features` adds fleet and per-drive age, calendar parts, and the era-availability flags plus era-gated rolling features for SMART 187 and 188 (`V16`). `add_multi_horizon_targets` adds the 7 / 14 / 30-day forward failure labels (`P07`). Drive-model target encoding is deferred to modeling (prior years only, `V18`/`O07`). Applied per drive-hash partition in `notebooks/10_feature_engineering_backblaze.py`; tested in `tests/test_backblaze_smart.py`.

## Cross-cutting conventions

- Each module exposes one or more pure functions taking Polars LazyFrames and returning LazyFrames with the new columns appended. No I/O.
- Each function's docstring cites the `eda_decisions.csv` row that motivates the feature.
- The Tier 3 module exists specifically to confirm the V12 inversion finding under preprocessing. The Risk-of-regression guard lives in `src/data/validation.py::assert_tier3_inversion`.

Modules land here once the corresponding notebook (10 or 11 for Google, post-`07c` for Backblaze) validates the logic and the relevant V-rows are populated.

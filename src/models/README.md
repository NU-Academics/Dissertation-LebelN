# `src/models/` - Ensemble Training and Online Learners

**Status:** `ensemble.py`, `classifier.py`, and `online.py` all populated and unit-tested, extracted from the RQ1, RQ2, and RQ5 notebooks respectively. Modules are extracted after the per-RQ notebooks validate the training logic against the methodology committed in Dissertation Proposal Chapter 3.

## Modules

- `ensemble.py`, populated - Reusable wrappers for the RQ1 tree-ensemble learners: `RandomForestWrapper`, `BalancedRandomForestWrapper`, `XGBoostWrapper`, `LightGBMWrapper`, `GradientBoostingWrapper`, and a `SoftVotingStack`, all satisfying one `EnsembleWrapper` protocol (`fit` / `predict_proba` / `feature_importances` / `save` / `load`). They accept Polars DataFrames at the boundary (converting to a dense `float32` array once per call), set cost-sensitive class weighting to the inverse class prior where the learner supports it (XGBoost via `scale_pos_weight` computed at fit; Gradient Boosting via balanced `sample_weight`), and leave SMOTE and the per-instance negative cap to the caller as training-only fold steps. `predict_proba` returns the 1-D positive-class probability. `build_wrapper(name, **params)` is the factory used by the modeling notebook and the hyperparameter search. Extracted from `notebooks/12_rq1_ensemble_google.py` (the three-level prediction architecture, `P06`); tested in `tests/test_ensemble.py`, and reused by the feature ablations (`notebooks/18_feature_ablation_google.py` and `notebooks/18_feature_ablation_backblaze.py`, `LightGBMWrapper` across feature sets and, on Backblaze, the fixed soft-voting stack retrained across the 10:1/20:1/40:1 working sets) and the Google Production-EVICT label sensitivity (`notebooks/18_sensitivity_prodevict_google.py`). Walk-forward cross-validation and Bayesian tuning (50 trials per family) are orchestrated by the notebook around these wrappers.
- `classifier.py`, populated - The non-ensemble classifiers for RQ2 (conflict resolution): `DecisionTreeWrapper`, `SVMWrapper` (linear SVM, whose signed `decision_function` is the positive-class score with `|coef_|` importances), and `SimpleNNWrapper` (one hidden layer, ReLU, sigmoid output, made picklable via custom get/setstate since Keras estimators do not pickle natively). They reuse the `EnsembleWrapper` protocol and the Polars boundary and pickle save/load from `ensemble.py`; the random forest used in RQ2 is `RandomForestWrapper` from `ensemble.py`, not duplicated. `build_classifier(name, **params)` mirrors `build_wrapper`. Extracted from `notebooks/13_rq2_conflict.py` (the >80% conflict-resolution success target, `P09`); tested in `tests/test_classifier.py`.
- `online.py`, populated - Incremental learners for RQ5 (concept drift), wrapping River behind an `OnlineLearner` protocol (`learn_one` / `predict_proba_one` / `predict_proba` / `save` / `load`) that mirrors the batch interface so a frozen ensemble and an adapting learner are driven by comparable calls. `AdaptiveRandomForestOnline` (the headline adaptive learner; each tree carries its own drift detector), `HoeffdingAdaptiveTreeOnline` (the cheap single-tree alternative), `OnlineBoostingOnline`, and `LogisticSGDOnline` (a standardizing pipeline plus incremental logistic regression, the linear reference), plus `OnlineSoftVotingEnsemble` with optional performance-based reweighting (an EWMA of each member's prequential loss, the ensemble-library mitigation for recurring drift). `frame_to_dicts` converts a Polars frame to River row dicts once per window; `build_online_learner(name, **params)` mirrors `build_wrapper`; `balanced_class_weights` matches the batch inverse-prior convention. Two deliberate design points: **prequential ordering is enforced structurally** (`learn_one` returns `self` and never a prediction, so predicting and learning cannot be fused into a call that scores an observation the model has already absorbed, which is the standard way a drift study manufactures a flattering curve), and **per-observation weight support is detected per learner rather than assumed**, so a River version that stops accepting weights fails visibly instead of silently training an all-negative model. Note on `P13`: River implements online bagging and online boosting but no online *gradient* boosting, so the boosting arm is incremental AdaBoost over Hoeffding trees (Freund & Schapire, 1997), named for what it computes (`V53`). Extracted from `notebooks/16_rq5_online.py`; tested in `tests/test_online.py`, including an exact checkpoint-and-resume equivalence test (Colab sessions expire at 12 hours, so resume must be bit-identical to an uninterrupted stream).

## Cross-cutting conventions

- Every stochastic operation uses `RANDOM_SEED = 42`, enforced repository-wide and locked by `tests/test_smoke.py::test_random_seed_constant_is_42`.
- Hyperparameter configurations are stored under `configs/` and loaded at runtime so model recipes are inspectable and version-controlled.
- Class-imbalance handling combines cost-sensitive learning (class weights = inverse prior) with SMOTE applied only inside training folds (`V02` for Google, `V17` for Backblaze).
- Held-out evaluation uses group-aware splits so no entity straddles train and test (instances hashed into buckets for the episode-grain failure models; the conflict entity, machine / instance / collection, for RQ2). Walk-forward (expanding-window) cross-validation runs inside the training period. Random k-fold is disallowed because both datasets carry temporal and grouping structure.

- Batch learners are trained once and scored; incremental learners in `online.py` are streamed in date order and must predict before they learn. The two are compared in RQ5 on identical natural-prevalence evaluation windows, so the comparison isolates the update policy rather than the data.

Modules land here once the corresponding notebook (12 through 16) validates the training logic and the per-RQ result tables land in `outputs/tables/`.
